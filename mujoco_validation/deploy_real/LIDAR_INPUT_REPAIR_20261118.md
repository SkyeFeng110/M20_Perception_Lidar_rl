# 1515 点云输入排查与修复

本次未启动自定义运动控制。结论来自板端抓包、DDS端点、逐段订阅及无电机预检查。

## 已定位的断点

1. **GOS驱动已启动，但没有原始输入。** 原厂GOS `rsdriver-network.service` 正在运行，两路报告 `ERRCODE_MSOPTIMEOUT`、点数为零。GOS网卡的被动抓包收到正常板间流量，无抓包丢包，却没有雷达包。
2. **雷达正常在AOS传感器网络发包。** AOS传感器网卡在一个抓包窗口内收到两路MSOP各约1.12万包，也收到DIFOP和IMU；这些数据没有送到GOS。不能据此归因于雷达未上电或硬件损坏。
3. **LIO输入QoS不兼容。** 在GOS恢复原始点云后，诊断订阅可以接收，LIO仍不处理。实际端点显示LIO的两个传感器订阅要求RELIABLE，而输入发布者提供BEST_EFFORT。
4. **GOS→AOS并非完全不通。** 修复前AOS已经收到状态包，但来源无效、接受数为零。上游恢复后，AOS完整无电机预检查通过。

## 最终链路

```text
前雷达 → AOS传感器网卡 → 原始UDP载荷转发 → GOS独立接收端口
       → GOS本地前雷达解码 → QoS适配 → LIO → registration → reader/sender → AOS
```

跨板只传原始小包，不编辑载荷和雷达时间戳。前雷达选择及几何参数沿用读取的1516参考配置，尚未在1515完成物理标定。
GOS本地QoS适配原样转发消息，使用独立话题；LIO只改两个输入话题名。
本次独立发布目录的DDS配置增加本地发现，保留板间观测通信。
唯一传感器工具参数台账是 `lidar_source_contract.json`，运行地址从现场接口/明确参数取得。

未修改原厂驱动、配置、服务、路由或全局网卡队列。原厂GOS旧端口驱动仍可能报警；本次策略使用独立端口的前雷达解码器，应查看新链路的运行证据。
注册质量、数据新鲜度、来源身份、目标关节保护及急停/阻尼路径均保留。

## 验证证据与边界

- 原始包转发的限时检查中，全部已接收的三类包成功发送，无发送错误；切换后AOS发送队列的累计丢包计数不再增加。
- GOS点云订阅检查收到连续非空帧。LIO随后完成KF及地图初始化，配准和健康观测均恢复。
- QoS适配核对覆盖全部消息字段、原始点数据哈希及原时间戳。CDR序列化的填充字节差异单独报告，不当成消息内容变化。
- 完整数值、最新验收结果和仍未完成项见 `JOINT_SAFETY_DEPLOYMENT_20261118.json`。
- 真实行走、上下楼后平地姿态、外参/关节零位标定均未验收；感知链恢复不能证明降噪或步态已改善。

调试时曾直接跨板发送完整点云，出现大量发送队列丢包；缩小DDS数据报未解决，故最终未采用该路径。
另一次启动因DDS线程尚在创建，短暂资源核验窗口不够而被拒绝；修复将等待放入有界启动预算，继续逐线程核验身份、核心、优先级和失败回滚。
诊断验收还发现发布包缺失独立的 `gos6d_verify_run`，由原保存源码补建，并先运行其无硬件测试。
失败轮次保留，不以局部通过覆盖失败。

## 运行和停止

当前感知辅助程序位于板端root tmux，脱离电脑SSH仍运行。它们需要机器人内部传感器和板间网络；电脑是否同一Wi-Fi不影响板端执行。

AOS会话：`model42900_raw_lidar`。
GOS会话：`model42900_front_lidar`、`model42900_lio_qos`，以及部署入口启动的GOS感知会话。
查看使用 `sudo tmux attach -t 会话名`；离开视图使用Ctrl-B再D，停止前台程序使用Ctrl-C。
停止辅助程序会使感知失效；AOS仍按既有新鲜度和故障门控处理。
重启后需要恢复这些板端会话；没有安装开机自启服务。
